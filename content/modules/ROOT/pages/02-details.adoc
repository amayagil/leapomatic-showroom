[#part-1]
== Part 1 — Tour the workflow in AAP

=== Know

_In Ansible Automation Platform, the upgrade is exposed as a *workflow template* named `WORKFLOW: Leapp-O-Matic RHEL 10 Migration`. The workflow chains five sequential steps, each backed by a job template that maps to the role's phases. Showing this first gives the customer a mental map of everything that follows._

[cols="1,2,3",options="header"]
|===
| Workflow Step | Job Template | Purpose

| Step 1
| `LEAPP 01: Preflight`
| Validates system requirements (memory, disk, OS compatibility).

| Step 2
| `LEAPP 02: RHSM Registration`
| Registers systems with Red Hat Subscription Manager.

| Step 3
| `LEAPP 03: Insights Registration`
| Registers systems with Red Hat Insights (required for LEAPP analysis).

| Step 4
| `LEAPP 04: Upgrade Execution`
| Runs the upgrade — repositories, package updates, and the LEAPP transformation to RHEL 10.

| Step 5
| `LEAPP 05: Post-Upgrade Verification`
| Validates the upgraded system (OS version, kernel, services) and cleans up artifacts.
|===

=== Show

**What I say:**

"Let me open Ansible Automation Platform and show you how this is assembled before we run anything. I don't want the upgrade to feel like a black box — I want you to see the pieces, so when we launch it live, you know exactly what's happening at each step."

**What I do:**

. In the *AAP Controller*, navigate to *Templates* → *Workflow Templates* and open `WORKFLOW: Leapp-O-Matic RHEL 10 Migration`.

. Open the workflow *Visualizer* and walk the customer through the five chained steps, left to right: *Preflight → RHSM Registration → Insights Registration → Upgrade Execution → Post-Upgrade Verification*.
* "Notice these run *in sequence*. That ordering is the whole safety story: preflight comes first, and if it fails, the destructive Upgrade Execution step never runs against that host."

. Open the `LEAPP 04: Upgrade Execution` job template and point out that it maps to the role's phases (repositories, update, LEAPP transformation). Show that AAP is configured to pull the role and its dependencies automatically.
+
image::aap-job-config.png[AAP job template configured to automatically download the role and its dependencies,width=600]

**What they should notice:**

* The entire upgrade is *one governed workflow* in AAP, not a runbook of manual steps.
* The steps are *sequential by design* — an early failure protects a host from the destructive steps.
* AAP pulls the role and its dependencies automatically; nothing is hand-installed on the fly.

**Business value callout:**

"This is what 'operationalized' looks like. Instead of a runbook that someone has to execute perfectly on every host, you have one repeatable, auditable workflow — with the safety checks and sequencing built in."

**If asked:**

Q: "What are the role's dependencies?"::
A: "It relies on two external Ansible roles — `role-rhsm-registration` for Red Hat Subscription Manager and `role-insights-registration` for Red Hat Insights, which LEAPP's pre-upgrade analysis requires. AAP downloads these automatically. The role also installs the packages the upgrade needs, like `leapp-upgrade` and `python3-dnf-plugin-versionlock`."

[#part-3]
== Part 3 — How the role decides (the gatekeeper)

=== Know

_The `role-rhel10-upgrader` role automates an end-to-end upgrade from RHEL 9 to RHEL 10 using the LEAPP utility. Rather than blindly running the upgrade, the role uses LEAPP's JSON report as a *gatekeeper*: it parses the report to decide whether the system is safe to upgrade or should stop to prevent a broken system._

The role's work is organized into sequential phases. Each phase must succeed before the next begins:

[cols="1,3",options="header"]
|===
| Phase | What It Does

| *Preflight*
| Validates system requirements — supported OS version (RHEL 9), sufficient free memory (≥ 2 GB), and disk space. This is the safety gate that stops unsafe upgrades before any destructive change.

| *Phase 1: Repositories*
| Sets RHEL 9.6 as the intermediate target and prepares the package repositories. This normalizes any RHEL 9.x host to a common baseline.

| *Phase 2: Update*
| Brings the current OS to the latest minor version within RHEL 9.x and reboots.

| *Phase 3: Upgrade*
| Runs the LEAPP pre-upgrade analysis, fetches and reviews the JSON report, then triggers the final transformation to RHEL 10 (followed by a reboot into RHEL 10).

| *Phase 4: Post-Upgrade Verification*
| After the reboot into RHEL 10, resets the Python interpreter to `/usr/bin/python3`, refreshes facts, validates the OS version and kernel, confirms RHEL 10 repositories and GPG keys, detects failed systemd units, cleans up LEAPP packages and DNF metadata, and scans for `.rpmnew`/`.rpmsave` configuration conflicts.
|===

=== Show

[NOTE]
====
*Presenter note:* This part is a short talk track to explain the "brains" of the role. You don't need a screen for it — a whiteboard gesture or pointing back at the workflow visualizer works. The payoff is that the customer understands *why* the upcoming failures are a feature, not a bug.
====

**What I say:**

"One last thing before we run it, so the results make sense. Inside that Upgrade Execution step, the role breaks the work into sequential phases, and each one has to succeed before the next runs. The very first is *preflight* — the safety gate. It checks the host is really on RHEL 9, has at least 2 GB free memory, and enough disk. If preflight fails, nothing destructive ever happens.

Then it sets up repositories and normalizes the host to a common RHEL 9.6 baseline, updates and reboots, and runs the LEAPP analysis and the actual transformation to RHEL 10. Afterward it verifies everything — OS version, kernel, repositories, GPG keys, services — and cleans up after itself.

The key idea: LEAPP's own report is used as a *gatekeeper*. The role reads it and *decides* whether it's safe to continue, rather than just barreling ahead. Keep that in mind, because in the very next run you're going to watch it decide *not* to continue — on purpose."

**What they should notice:**

* The *first* phase is a safety check, by design — validation happens before any change.
* Version normalization means a messy, mixed-version fleet doesn't need manual alignment first.
* The role cleans up after itself and *verifies* the result, so you're not left guessing whether the upgrade worked.

**If asked:**

Q: "Do I need every host on the same RHEL 9 minor version first?"::
A: "No — that's a deliberate design point. During the repositories phase the role normalizes any RHEL 9.x host to RHEL 9.6 as the intermediate target before upgrading to RHEL 10. No manual pre-upgrade version alignment needed. We'll see that live when 9.5 and 9.7 both upgrade cleanly."

Q: "Where do the credentials live?"::
A: "Never in the role or the playbooks. The RHSM username and password are held in an AAP credential and injected at runtime — which is the first thing I'll configure when we move into the live run."

With the setup clear, continue to xref:rhel10-upgrader-aap.adoc[The Live Demo] to configure the credential and run the two workflows.
